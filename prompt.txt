Создай с нуля небольшой учебный движок для классического слота с полем 5 × 3. Главная цель — простая, понятная архитектура с разделением ответственности, которую легко читать и расширять.

СТЕК И ГРАНИЦЫ

Используй TypeScript, Vite и PixiJS. Проект должен быть самостоятельным: не подключай внутренние пакеты существующего SDK и не переноси его классы. Используй архитектурные идеи, но реализуй существенно меньшую систему.

Не добавляй сервер, сетевые запросы, реплеи, спецэффекты, Spine, GSAP, физику, звук, автоспины, бонусные игры, расчёт вероятностей и таблиц выплат. Не копируй существующие ассеты. Изображения символов замени цветными прямоугольниками с буквами A–E, созданными средствами PixiJS. Используй системный шрифт.

Для максимальной простоты при спине комбинация заменяется мгновенно, без анимации вращения и искусственных задержек.

ПОВЕДЕНИЕ ДЕМО

Сделай две сцены:
1. MenuScene: название и кнопка «Начать».
2. SlotScene: поле 5 × 3, кнопки «Spin» и «В меню», текст «Выигрыш: ...».

Результат каждого спина бери из локального файла src/data/spins.json, импортированного в проект как данные. Никакого fetch и генерации случайного результата. Используй записи последовательно; индекс увеличивай только после успешного завершения сценария. После последней записи возвращайся к первой. При ошибке следующий Spin повторяет ту же запись.

Формат JSON:
{
  "spins": [
    {
      "id": "spin-1",
      "grid": [
        ["A", "B", "C", "D", "E"],
        ["B", "C", "D", "E", "A"],
        ["C", "D", "E", "A", "B"]
      ],
      "winAmount": 0
    },
    {
      "id": "spin-2",
      "grid": [
        ["A", "A", "A", "A", "A"],
        ["B", "C", "D", "E", "B"],
        ["C", "D", "E", "B", "C"]
      ],
      "winAmount": 20
    }
  ]
}

grid индексируется как [строка][барабан]: три строки по пять символов. Выигрыш не вычисляй, а отображай winAmount из той же записи. Перед использованием проверь размер матрицы, допустимость символов и числовое неотрицательное значение выигрыша. Исходные записи не изменяй. При входе в SlotScene показывай первую комбинацию и нулевой выигрыш; первый Spin использует первую запись. Для нового экземпляра сцены последовательность начинается заново.

МИНИМАЛЬНАЯ ECS

Сделай настоящую небольшую ECS:
- Entity — числовой идентификатор.
- Компоненты — данные в типизированных Map<Entity, Component>.
- Системы — поведение, работающее с нужными наборами компонентов.
- World создаёт и удаляет сущности, хранит компоненты и позволяет выбирать сущности по их наличию.

Достаточно компонентов Position, Rectangle, Text, Button и GridCell. Button хранит идентификатор действия и enabled, GridCell — строку, колонку и ключ символа. Данные компонента не должны содержать игровой алгоритм или собственный update().

Выдели простые системы:
- GridSystem обновляет компоненты 15 ячеек по переданной матрице.
- InputSystem связывает клики с действиями активной сцены.
- RenderSystem создаёт и синхронизирует Pixi-объекты по компонентам, а при удалении освобождает их.

Pixi-объекты храни в слое отображения, отдельно от данных компонентов. Не создавай классы игровых сущностей с наследованием и индивидуальным update(). Не добавляй archetypes, многопоточность, ECS-фреймворк, сложный планировщик, DI-контейнер и глобальную шину событий.

АВТОМАТ СОСТОЯНИЙ

У SlotScene должен быть небольшой автомат раунда:
- idle — можно начать спин;
- running — выполняется сценарий;
- error — показана ошибка, следующий Spin позволяет повторить попытку.

Переходы: idle → running → idle; running → error; error → running.

Автомат разрешает запуск только одного спина. Во время running кнопки Spin и «В меню» недоступны. Не вводи дополнительные независимые флаги isSpinning или isBusy: доступность UI определяется состоянием автомата. Состояние running может быть коротким; не добавляй задержки ради его видимости.

ПОСЛЕДОВАТЕЛЬНЫЙ ИСПОЛНИТЕЛЬ ДЕЙСТВИЙ

Отдели автомат состояний, подготовку сценария и выполнение действий.

RoundSource выбирает запись JSON. Чистая функция buildActions(result) создаёт два типизированных действия:
1. setGrid с матрицей символов.
2. setWin с суммой выигрыша.

Представь действия различаемым объединением TypeScript по полю type. ActionRunner получает список и реестр обработчиков. Его основная логика:

для каждого действия:
    выбрать обработчик по type;
    если обработчика нет — выдать понятную ошибку;
    вызвать обработчик и дождаться его завершения через await;
    только после этого перейти к следующему действию.

Обработчик может быть синхронным или возвращать Promise. setGrid обращается к GridSystem, setWin обновляет компонент текста выигрыша. ActionRunner не должен знать про сетку, кнопки и конкретные Pixi-объекты. Системы не читают общую очередь и не извлекают из неё действия самостоятельно. Единственный владелец порядка выполнения — ActionRunner.

Поток спина:
клик → проверка FSM → running → текущая запись JSON → buildActions → ActionRunner → увеличение индекса → idle.
При исключении FSM переходит в error, сообщение выводится на экран, интерфейс остаётся работоспособным.

СЦЕНЫ И UI-КОМПОНЕНТЫ

SceneManager регистрирует фабрики сцен и управляет одной активной сценой. У сцены есть enter(), exit() и dispose(). Каждая сцена владеет своим World, корневым Pixi-контейнером и обработчиками ввода. При переключении предыдущая сцена освобождает объекты и подписки. Новая сцена создаётся через зарегистрированную фабрику. Смену сцены во время running не разрешай; отдельная система отмены для этого демо не нужна.

UI создавай через небольшие переиспользуемые фабрики createButton(), createLabel(), createPanel(). Фабрики составляют сущности из обычных ECS-компонентов, а не создают отдельный параллельный UI-фреймворк. Клик передаёт действие обработчику активной сцены. Макет задавай простыми координатами, без универсальной системы layout и привязок.

Перерисовывай сцену после изменений. Собственный постоянный requestAnimationFrame-цикл для статичного демо не нужен. Не опрашивай очередь действий каждый кадр.

РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ

- World — сущности и данные компонентов.
- Системы — работа с компонентами, ввод и отображение.
- SceneManager и сцены — создание, переключение и освобождение игрового окружения.
- FSM — допустимые состояния раунда и переходы.
- RoundSource — последовательное чтение JSON.
- buildActions — преобразование результата в сценарий.
- ActionRunner — последовательное выполнение обработчиков.
- UI-фабрики — удобное создание кнопок, подписей и панелей.

Не делай универсальный движок «на будущее». Не добавляй уровни абстракции, которые не нужны двум сценам и двум действиям. Предпочитай небольшие конкретные модули и явные зависимости.

ГОТОВЫЙ РЕЗУЛЬТАТ

Предоставь запускаемый проект и короткую инструкцию запуска. Объясни, где добавить новую сцену, компонент, символ и обработчик действия.

Проверь, что:
- комбинации последовательно берутся из JSON;
- повторный клик не запускает второй сценарий одновременно;
- следующее действие действительно ждёт завершения предыдущего;
- неизвестное действие и некорректные данные дают понятную ошибку;
- после переходов Menu → Slot → Menu → Slot не дублируются обработчики;
- существующие изображения, код SDK и игровые ассеты не скопированы.
